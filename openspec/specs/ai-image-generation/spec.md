## Requirements
### Requirement: Image generation is gated, metered and refused honestly

The system SHALL require the image plan feature before generating, SHALL charge a cost class above
text generation, and SHALL refuse rather than degrade when the installation cannot generate images.

#### Scenario: Plan excludes the feature

- **WHEN** an organization whose plan excludes image generation requests an image
- **THEN** the request is refused as feature-locked, naming the minimum plan
- **AND** no allowance is reserved and no provider call is made

#### Scenario: Installation cannot generate images

- **WHEN** the configured provider dialect cannot generate images
- **THEN** the request is refused as capability-unavailable
- **AND** the capabilities endpoint reports that this installation cannot generate images, so the
  interface hides the action instead of offering one that would fail

#### Scenario: Allowance is exhausted

- **WHEN** the organization has less remaining allowance than an image costs
- **THEN** the request is refused as budget-exceeded before the provider is called

#### Scenario: Provider fails after the reservation

- **WHEN** the provider fails or returns something unusable
- **THEN** the reserved allowance is returned to the organization
- **AND** no media record is created

### Requirement: The requested shape is an aspect ratio, not a vendor resolution

The system SHALL accept the target shape as an aspect ratio drawn from a closed set the networks
use, and the translation from ratio to whatever dimensions a provider accepts SHALL live in the
provider adapter.

#### Scenario: A ratio is requested

- **WHEN** a supported aspect ratio is requested
- **THEN** the returned image matches that ratio
- **AND** its recorded width and height are the real transformed dimensions
- **AND** no use case, route or interface names a pixel resolution

#### Scenario: A channel is named instead of a ratio

- **WHEN** a target channel is given
- **THEN** the ratio is chosen as one that channel accepts

#### Scenario: An unsupported ratio is requested

- **WHEN** a ratio outside the supported set is requested
- **THEN** the request is refused as invalid before any provider call

### Requirement: Generated bytes are validated, stored and marked as generated

The system SHALL validate the returned bytes by inspecting the content itself rather than trusting
the provider's declared type, SHALL store the image in the organization's library through the same
path uploads use, and SHALL record that the asset was generated, with which prompt and which model.

#### Scenario: Usable image returned

- **WHEN** the provider returns a supported image
- **THEN** a media record is created in the requesting organization's library
- **AND** the record states that its source is generation, and stores the prompt and the model

#### Scenario: Database write fails after storing bytes

- **WHEN** storage accepts the generated bytes but the media record cannot be created
- **THEN** the stored object is deleted best-effort
- **AND** the original database error is returned and the allowance is released

#### Scenario: Response is not a supported image

- **WHEN** the returned bytes are not a supported image format, whatever the declared type says
- **THEN** the request fails and no media record is created
- **AND** the allowance is returned

#### Scenario: Image exceeds the installation's size ceiling

- **WHEN** the returned image is larger than the configured image ceiling
- **THEN** the request fails with the too-large error rather than storing it

#### Scenario: Provenance is visible

- **WHEN** a generated image is listed in the library
- **THEN** the listing distinguishes it from an uploaded file

#### Scenario: The prompt is not audited

- **WHEN** a generation is recorded in the audit log
- **THEN** the entry names the organization, the actor and the operation
- **AND** it contains neither the prompt nor the generated bytes

### Requirement: Repeating the same request does not charge twice

The system SHALL treat a repeated image request carrying the same idempotency key as the same
request, returning the original result without generating again or charging again.

#### Scenario: Same key replayed

- **WHEN** the same request is sent twice with the same idempotency key
- **THEN** the second call returns the first result
- **AND** the allowance is charged once and the provider is called once

#### Scenario: Same key, different body

- **WHEN** the same idempotency key arrives with a different request body
- **THEN** the request is refused as a conflict rather than silently returning the wrong image

#### Scenario: No key supplied

- **WHEN** no idempotency key is supplied
- **THEN** the request proceeds, because regenerating on purpose is a legitimate action

#### Scenario: Browser retries the same logical submission

- **WHEN** transport retries a browser submission with unchanged prompt and target
- **THEN** every retry carries the same idempotency key

#### Scenario: Supported deployment coordinates replay

- **WHEN** the paid endpoint runs in a supported deployment
- **THEN** the required Redis coordination service stores the claim and completed response
- **AND** an integration test proves the replay before release
