## Context

Image generation crosses provider adaptation, paid allowance, media storage,
PostgreSQL provenance, HTTP/MCP surfaces and the browser. The protocol accepts
only a few native pixel sizes while the product contract promises exact social
aspect ratios. Storage and database writes are not one transaction, and Redis
idempotency is optional at package level even though supported deployments
require `REDIS_URL`.

## Goals / Non-Goals

**Goals:**

- advertise image generation only when an operator explicitly configured it;
- return bytes with the exact requested aspect ratio;
- avoid charging or leaving storage objects behind after a failed write;
- send a stable idempotency key for each browser generation attempt;
- prove migration compatibility, Redis replay and UI behavior locally.

**Non-Goals:**

- implementing another provider protocol;
- changing the platform-wide Redis fail-open contract;
- making media deletion remove files referenced by scheduled posts;
- generating more than one image per request.

## Decisions

1. `AI_IMAGE_MODEL` is an explicit capability opt-in. Without it, the
   chat-completions adapter omits `generateImage`; `AI_MODEL` is never assumed
   to draw. This avoids a false-positive capability for text-only models.
2. Pixel vocabulary stays inside `packages/core/src/infra/ai`. The adapter asks
   for the nearest native size, reads the real returned dimensions, then uses
   `sharp` to center-crop to the largest exact integer multiple of the requested
   ratio. `sharp` is a direct runtime dependency of `@manypost/core`; input
   pixels remain bounded and no enlargement is performed.
3. The use case still sniffs the transformed bytes and records their real
   dimensions. Provider-declared MIME and dimensions are not trusted.
4. After `storage.put`, a failed `media.create` triggers a best-effort
   `storage.delete`. Cleanup failure never replaces the original database
   error. The same helper is reused by ordinary uploads so the invariant is not
   image-generation-specific.
5. The browser creates one UUID for a logical submission and reuses it for
   transport retries of the same prompt/aspect/channel fingerprint. A changed
   request gets a new key.
6. HTTP idempotency remains the existing Redis adapter. Supported runtime env
   requires `REDIS_URL`; package-level Redis failure still fails open as
   documented by the platform. E2E with disposable Redis is therefore a release
   gate for this paid endpoint, not an architectural rewrite of all mutation
   idempotency.
7. Migration `0007` remains additive and generated by Drizzle. Validation runs
   on both an empty database and a database at the preceding schema with
   existing media rows. Generated OpenAPI files are refreshed only through the
   existing generator.

## Risks / Trade-offs

- [Cropping may remove edge content] → use centered crop, request the closest
  native size, and show the result for review before use.
- [Image decompression can consume excessive resources] → retain Sharp's input
  pixel limit and the existing encoded-byte ceiling; reject unreadable output.
- [Redis outage can allow a duplicate paid effect] → supported deploys require
  Redis, health/E2E verify it, and the UI always supplies a stable key. Changing
  the platform-wide failure policy needs a separate cross-cutting change.
- [Storage cleanup can fail] → preserve the primary error and leave an
  observable orphan for operational cleanup rather than masking the cause.

## Migration Plan

1. Apply additive migration `0007`; old application versions ignore the new
   columns.
2. Deploy API and web with `AI_IMAGE_MODEL` unset to keep generation disabled.
3. Configure an image-capable model and verify `/v1/capabilities` before
   exposing the action.
4. Rollback code first if needed. Dropping the provenance columns is optional;
   keeping them is backward-compatible. Existing media bytes are never removed.
