## MODIFIED Requirements

### Requirement: Image generation is gated, metered and refused honestly

The system SHALL require the `ai_image` plan feature before synchronous or
asynchronous image generation, SHALL use an image-specific customer-credit
class above text generation and SHALL refuse rather than degrade when the
installation lacks an eligible image recipe/provider.

The synchronous compatibility endpoint SHALL preserve its existing safe
commit/release behavior. An asynchronous generation SHALL use its durable
generation-bound reservation: a proven terminal outcome with no usable image
releases customer credits, while possible provider acceptance SHALL enter
`submission_uncertain` and MUST NOT release credits or retry blindly.

#### Scenario: Plan excludes the feature

- **WHEN** an organization whose plan excludes image generation requests a synchronous or asynchronous image
- **THEN** the request is refused as feature-locked, naming the minimum plan
- **AND** no allowance, provider spend or capacity is reserved
- **AND** no provider call is made

#### Scenario: Installation cannot generate images

- **WHEN** no configured active recipe can perform the requested image operation
- **THEN** the request is refused as capability-unavailable
- **AND** capabilities report the operation unavailable so the interface does not offer it

#### Scenario: Allowance is exhausted

- **WHEN** the organization has less remaining allowance than the image operation's declared maximum
- **THEN** the request is refused as budget-exceeded before provider submission

#### Scenario: Synchronous provider fails after reservation

- **WHEN** the compatibility provider safely fails or returns unusable content
- **THEN** its synchronous reservation is released
- **AND** no media record is created

#### Scenario: Asynchronous provider proves terminal failure

- **WHEN** an asynchronous attempt truthfully terminates without a usable image
- **THEN** generation-bound customer credits are released exactly once
- **AND** incurred provider monetary cost remains separately recorded

#### Scenario: Asynchronous submission may have been accepted

- **WHEN** the image provider may have accepted a paid asynchronous submission but no run identity is known
- **THEN** the generation enters `submission_uncertain`
- **AND** its customer/provider reservations remain held for reconciliation
- **AND** no automatic retry or fallback creates another image

### Requirement: Generated bytes are validated, stored and marked as generated

The system SHALL validate generated image bytes by inspecting content rather
than trusting provider-declared MIME, filename or dimensions. A usable image
SHALL be stored through the active organization-scoped media storage path and
recorded as `source='ai'` with non-content model/recipe provenance.

New code MUST NOT store a plaintext generation prompt permanently in
`media.generation_prompt`. Canonical prompt/options SHALL be encrypted in
generation or compatibility retention metadata and cleared no later than 30
days after creation. Synthetic source, model/recipe and output-generation link
MAY remain after prompt purge.

#### Scenario: Usable synchronous image is returned

- **WHEN** the compatibility provider returns one supported image
- **THEN** inspected bytes are stored in the requesting organization's library
- **AND** the media record marks its source and non-content model provenance as generated
- **AND** no plaintext prompt is permanently stored on the media record

#### Scenario: Usable asynchronous image is returned

- **WHEN** asynchronous image ingestion validates and stores its primary object
- **THEN** one organization-scoped generated media record is linked as the generation's primary output
- **AND** provider temporary references are not used as the media library URL

#### Scenario: Synchronous database write fails after storing bytes

- **WHEN** compatibility storage accepts generated bytes but its media record cannot be created
- **THEN** the stored object is deleted best-effort
- **AND** the original database error is returned
- **AND** the synchronous allowance reservation is released

#### Scenario: Async final transaction fails after object storage

- **WHEN** asynchronous storage accepts the deterministic primary object but media/output finalization rolls back
- **THEN** the image remains non-visible and the generation remains non-terminal
- **AND** ingestion retries the same allocated identity without provider resubmission

#### Scenario: Response is not a supported image

- **WHEN** returned bytes are not a supported image format regardless of declared type
- **THEN** no user-visible media/output record is committed
- **AND** asynchronous recovery does not resubmit inference merely because validation failed

#### Scenario: Image exceeds the installation ceiling

- **WHEN** the returned image exceeds configured or snapshotted byte/dimension bounds
- **THEN** ingestion fails with a sanitized too-large/invalid-output classification
- **AND** no user-visible media is created

#### Scenario: Provenance is visible

- **WHEN** a generated image is listed in the media library
- **THEN** the listing distinguishes it from uploaded media
- **AND** it can retain non-content model/recipe provenance after prompt expiry

#### Scenario: Prompt is not audited or logged

- **WHEN** image generation activity is logged, metered or written to the audit log
- **THEN** records may identify organization, actor, operation, recipe and outcome
- **AND** they contain no prompt, generated bytes, signed URL, credential or raw provider body

#### Scenario: Prompt-retention deadline passes

- **WHEN** encrypted image-generation content becomes older than 30 days
- **THEN** the retention worker irreversibly clears it from application records
- **AND** generated media and non-content provenance remain valid

### Requirement: Repeating the same request does not charge twice

The system SHALL scope image idempotency by organization and canonical request.
Repeating the same key/request SHALL return the original result/resource without
another provider call or charge; reusing the key with another canonical request
SHALL conflict.

For compatibility, `POST /v1/ai/image` SHALL continue to accept an optional
idempotency key and use its existing supported-deployment coordination.
`POST /v1/ai/media/generations` SHALL require an idempotency key and persist the
claim/fingerprint/result in PostgreSQL as part of the durable generation
transaction. Redis MUST NOT be authoritative for asynchronous paid
idempotency.

#### Scenario: Same synchronous key is replayed

- **WHEN** the same compatibility request is sent twice with the same idempotency key
- **THEN** the second call returns the first media result
- **AND** allowance is charged once and the provider is called once

#### Scenario: Same async key is replayed

- **WHEN** the same organization repeats an asynchronous image request with the same key and canonical body
- **THEN** the original generation resource is returned
- **AND** no second reservation, queue effect, provider attempt or image output is created

#### Scenario: Same key is used with different body

- **WHEN** the same organization reuses an image idempotency key with different normalized input or options
- **THEN** the request is refused as conflict rather than returning or generating the wrong image

#### Scenario: No key is supplied to compatibility endpoint

- **WHEN** no idempotency key is supplied to `POST /v1/ai/image`
- **THEN** the request proceeds because intentional synchronous regeneration remains compatible

#### Scenario: No key is supplied to async endpoint

- **WHEN** no idempotency key is supplied to asynchronous image generation
- **THEN** creation is refused before reservation or provider submission

#### Scenario: Browser retries the same logical submission

- **WHEN** transport retries an unchanged image submission
- **THEN** every retry carries the same idempotency key

#### Scenario: Browser changes a cost-affecting option

- **WHEN** the person changes prompt, source image, aspect or quality after a logical submission
- **THEN** the next intended generation uses a new idempotency key

#### Scenario: Redis is unavailable during async replay

- **WHEN** Redis coordination is unavailable and an asynchronous request is replayed
- **THEN** PostgreSQL still returns the original generation or the key/body conflict
- **AND** no duplicate paid effect is authorized

## ADDED Requirements

### Requirement: Guided asynchronous image operations create one primary image

The system SHALL provide durable `social-image-create` and
`social-image-edit` operations. A successful operation SHALL create exactly one
new primary generated-image media record. The existing synchronous
`POST /v1/ai/image` contract SHALL remain available and SHALL NOT be represented
as having asynchronous recovery guarantees.

`social-image-edit` SHALL require one supported source image owned by the
authenticated organization and SHALL never mutate or replace that source media.

#### Scenario: New image is generated asynchronously

- **WHEN** an authorized caller creates `social-image-create` with valid input and accepted credits
- **THEN** the API returns a durable generation resource
- **AND** success links exactly one new organization-scoped image as its primary output

#### Scenario: Owned image is edited

- **WHEN** an authorized caller creates `social-image-edit` with one owned supported source image
- **THEN** success stores a separate new generated image
- **AND** the source media bytes and metadata remain unchanged

#### Scenario: Editing source belongs to another organization

- **WHEN** a caller names an image outside the authenticated organization
- **THEN** the request returns not found before customer/provider reservation
- **AND** no provider input or submission is created

#### Scenario: Editing source is not a supported image

- **WHEN** the referenced owned media is not a supported image or exceeds the recipe input bounds
- **THEN** creation is refused before external submission

#### Scenario: Provider returns more than one candidate

- **WHEN** an image provider returns multiple candidates
- **THEN** the immutable recipe applies its deterministic primary-selection rule
- **AND** at most one image is exposed or charged by the generation

#### Scenario: Existing client uses compatibility endpoint

- **WHEN** an existing client calls `POST /v1/ai/image`
- **THEN** its documented request, response, `economy|quality`, idempotency and credit behavior remain valid

### Requirement: Image controls expose product options, not provider internals

Image generation SHALL accept supported Manypost product options such as the
closed aspect-ratio set and `economy|quality` mode where declared by the active
recipe. The server SHALL translate those options through the immutable
adapter/model recipe and calculate customer credits; the browser MUST NOT
supply provider model, pixel preset, sampler, seed, endpoint or price.

This change MUST NOT advertise or accept LoRA, ControlNet, IP-Adapter or
similar advanced reference/guidance controls. Adding one requires a separate
provider-capability change covering support, rights, retention and cost.

#### Scenario: Economy mode is selected

- **WHEN** a caller selects `economy` for a recipe that supports it
- **THEN** the server snapshots the approved economy mapping and disclosed customer credits
- **AND** no provider-native quality or model field crosses the public contract

#### Scenario: Quality mode is selected

- **WHEN** a caller selects `quality` for a recipe that supports it
- **THEN** the server snapshots the approved quality mapping and disclosed customer credits
- **AND** active execution retains that snapshot after catalogue promotion

#### Scenario: Supported aspect ratio is selected

- **WHEN** a caller selects a ratio from the closed Manypost set
- **THEN** the adapter translates the ratio to provider-native dimensions
- **AND** the durable media records inspected output width and height

#### Scenario: Unsupported advanced control is supplied

- **WHEN** a request supplies LoRA, ControlNet, IP-Adapter, seed, sampler or another non-launch control
- **THEN** public schema/capability validation refuses it before quote or submission
- **AND** no local inference fallback is attempted

#### Scenario: Image recipe is promoted

- **WHEN** an operator promotes a reviewed image recipe
- **THEN** new image generations use its mapping
- **AND** existing generations retain their persisted recipe and charge
